## Requirements

### Requirement: Aim point computed from marker correspondences
The system SHALL compute a screen-space aim point from a set of marker
correspondences, each pairing a marker's known screen-plane position
(millimetres, from `markers.toml`) with its detected image-plane
position (pixels), by computing a homography from screen plane to image
plane via `findHomography` with RANSAC over all correspondences,
inverting it, and mapping the image centre through the inverse.

#### Scenario: Recovering a known aim point from synthetic correspondences
- **WHEN** the solver is given correspondences generated by applying a
  known ground-truth homography to the known screen-plane marker
  corners
- **THEN** the solver returns an aim point within a documented tolerance
  of the point the ground-truth homography actually maps the image
  centre to

#### Scenario: Insufficient correspondences
- **WHEN** the solver is given fewer than four marker correspondences
- **THEN** the solver raises a clear error identifying that a homography
  requires at least four correspondences, and does not attempt to call
  `findHomography`

### Requirement: Solver is decoupled from config and detection I/O
The solver SHALL accept marker correspondences as plain in-memory data
(screen-plane points paired with image-plane points) and SHALL NOT read
`markers.toml` or invoke a detector itself, so it can be exercised with
synthetic correspondences without any file or camera I/O.

#### Scenario: Synthetic correspondences require no config file or detector
- **WHEN** a test constructs correspondences entirely from a known
  ground-truth transform, with no `markers.toml` file present and no
  detector invoked
- **THEN** the solver runs to completion and returns a result, exactly
  as it would given correspondences sourced from real config and
  detection output

### Requirement: Solver composes correctly with real detection on a synthetic image
The system SHALL be verifiable, without a camera, by rendering marker
patterns into a synthetic image via a known perspective warp, running
the project's marker detector against that rendered image to obtain
image-plane corners, and passing those detected corners (paired with
the markers' known screen-plane positions) into the solver.

#### Scenario: Detector output on a synthetic image round-trips through the solver
- **WHEN** marker patterns are rendered onto a canvas and warped by a
  known homography, and the resulting image is run through the marker
  detector to obtain corners
- **THEN** passing those detected corners into the solver yields an aim
  point within a documented tolerance of the point the known warp
  actually maps the image centre to

### Requirement: Per-frame solver output forms a temporally coherent trajectory
The system SHALL produce a temporally coherent trajectory of aim points
when the solver is applied independently, once per frame, to each frame
of a temporally coherent input sequence (a smoothly moving camera
observing a fixed marker layout): consecutive-frame aim points SHALL
track the known consecutive-frame camera motion, without discontinuities
the input motion does not justify. The solver holds no state between
calls; this requirement constrains the trajectory formed by independent
per-call outputs, not any internal temporal logic.

#### Scenario: Consecutive frames of a smooth camera sweep produce a smooth aim-point trajectory
- **WHEN** the solver is called once per frame, in order, on
  correspondences detected from each frame of a rendered sequence
  depicting a smoothly moving camera
- **THEN** for each pair of consecutive frames, the difference between
  their recovered aim points matches the difference between their known
  ground-truth aim points, within a documented tolerance

#### Scenario: Each frame's recovered aim point matches its own ground truth
- **WHEN** the solver is called on correspondences detected from a single
  frame of the sequence
- **THEN** the recovered aim point matches that frame's independently
  computed ground-truth aim point (derived from the rendering camera's
  known pose, not from the solver's own homography math) within a
  documented tolerance

### Requirement: Solver reports the geometric conditioning of each solve
The solver SHALL report, alongside the aim point, whether that aim point
lies inside the convex hull of the screen-plane correspondence points,
the signed distance from the aim point to that hull in millimetres, and
the extent of the correspondence points. Reprojection error SHALL NOT be
relied upon for this purpose: an exactly-determined fit from a single
marker has near-zero reprojection error while its aim point may be
badly wrong, so reprojection error is anti-correlated with accuracy in
exactly the case this signal exists to flag.

#### Scenario: Aim point inside the marker footprint is reported as interpolated
- **WHEN** the solver is given correspondences from markers spread
  around the aim point, so that the aim point falls within their convex
  hull
- **THEN** the result reports the aim point as inside the hull, with a
  signed distance indicating it is interior

#### Scenario: Aim point beyond the marker footprint is reported as extrapolated
- **WHEN** the solver is given correspondences from a single marker, or
  from markers clustered such that the aim point falls outside their
  convex hull
- **THEN** the result reports the aim point as outside the hull, with a
  signed distance indicating how far beyond the fitted region it lies

#### Scenario: Conditioning is reported without changing the aim point
- **WHEN** the same correspondences are solved
- **THEN** the reported aim point is identical to what the solver would
  produce without the conditioning fields, which are additional data and
  never alter the solution

### Requirement: Solver degrades predictably as marker visibility drops
The solver SHALL return a best-effort aim point whenever at least four
correspondences are available, regardless of how poorly those
correspondences are distributed, and SHALL NOT refuse or substitute a
fallback value on conditioning grounds alone. Deciding what to do about
a poorly conditioned aim point is the consumer's responsibility.

#### Scenario: A well-distributed subset of markers stays accurate
- **WHEN** only some markers are visible but they span the aim point --
  for example markers on opposite sides of the panel
- **THEN** the recovered aim point matches ground truth within a
  documented tolerance comparable to the full-visibility case

#### Scenario: A poorly distributed subset still returns an answer, flagged
- **WHEN** only markers clustered on one edge, or a single marker, are
  visible, so the aim point is extrapolated well outside them
- **THEN** the solver still returns an aim point rather than raising
- **AND** the result's conditioning fields report the aim point as
  outside the correspondence hull

#### Scenario: No visible markers cannot be solved
- **WHEN** a frame contains no detectable markers, so fewer than four
  correspondences are available
- **THEN** the solver raises the insufficient-correspondences error
  rather than returning an aim point
