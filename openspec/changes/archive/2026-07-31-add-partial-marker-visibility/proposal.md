## Why

Every existing test of `solve.py` runs with 7-8 of 8 markers visible.
Real play is not like that: a player standing close to the TV, a
narrow-FOV camera, an off-axis angle, a hand over the barrel, or a fast
swing all leave only part of the marker layout in frame. README already
anticipates this ("a narrow-FOV camera at close range will not see the
corners", which is why the layout has edge midpoints at all) and states
"One marker is sufficient. Four corner points is a complete
homography."

Measuring against the existing rendered fixture shows that claim is
geometrically true but practically misleading, and that the current code
gives the caller no way to tell a good solve from a useless one:

| correspondences used | aim error |
| --- | --- |
| all 7-8 markers | 1.4mm median, 1.6mm max |
| 4 markers | 1.5mm median, 2.0mm max |
| 2 markers, opposite sides of the panel | 0.8mm |
| 2 markers, both on the same edge | 17.6mm median, 39.5mm max |
| 1 marker | 153mm median, up to **2037mm** |

So accuracy is governed by the *geometric spread of the correspondences
relative to the aim point*, not by marker count. One 80mm marker spans
80mm of screen plane, and the aim point is typically hundreds of mm
away — that is extrapolation far outside the convex hull of the fitted
points, where sub-pixel corner error is amplified without limit. A 2037mm
error on a 1220mm panel is an aim point nowhere near the screen.

Worse, the one quality signal `solve.py` already returns is inverted
here. Reprojection error for a single marker is **0.000px** — 4 points
and 8 degrees of freedom fit exactly — while the aim point is 162mm
wrong; the all-markers solve has the *highest* reprojection error
(2.2px) and the *best* accuracy. A downstream consumer that trusted
reprojection error would prefer precisely the worst solves.

A separate, harder limit shows up when rendering the same scene from a
range of distances, aiming at screen centre: below roughly 1.8m at 45°
FOV, the bezel markers leave the frame entirely and there is nothing to
solve from at all.

| camera distance | markers detected | aim error |
| --- | --- | --- |
| 700 / 1000 / 1400mm | 0 | no solve possible |
| 1800mm | 2 (opposite midpoints) | 0.8mm |
| 2200mm and beyond | 8 | 1.0-1.6mm |

## What Changes

- Add a geometric-conditioning signal to `solve.py`'s result: whether
  the aim point falls inside the convex hull of the screen-plane
  correspondences, its signed distance to that hull, and the spread of
  the correspondences. This is what distinguishes an interpolated aim
  point from an extrapolated one, which reprojection error provably
  cannot.
- `solve.py` continues to return a best-effort answer in poorly
  conditioned cases rather than refusing. Deciding what to do about a
  low-confidence aim point (hold last good pose and decay, per README's
  "Dropout" note) is the consumer's call, and the consumer does not
  exist yet.
- Reorganise the solver's end-to-end coverage into **two decks**:
  - **Full visibility** — the whole marker layout in frame. Tightest
    tolerances; this is the accuracy the system is capable of.
  - **Partial visibility** — only some markers in frame, covering both
    a well-conditioned subset (markers spanning the aim point) and an
    ill-conditioned one (markers clustered on one edge, aim point
    extrapolated), plus the zero-marker case.
- Add a close-range rendered fixture where markers genuinely leave the
  frame, so the partial deck exercises detection and solving together
  rather than only synthetic subsetting.
- Document the working-distance floor and the geometry-not-count
  finding in README, next to the existing marker-layout guidance.
- **Not** changing the algorithm to fix the sparse case. The real fix
  is pose estimation from a single marker of known physical size
  (`solvePnP`) instead of homography extrapolation, which needs camera
  intrinsics — an unbuilt milestone. Noted as follow-up, not attempted.

## Capabilities

### New Capabilities
(none)

### Modified Capabilities
- `homography-solve`: adds a requirement that the solver report the
  geometric conditioning of each solve, and requirements covering
  behaviour when only part of the marker layout is visible — neither of
  which the existing requirements constrain, since they all assume a
  well-populated correspondence set.

## Impact

- `src/boresight/solve.py`: `SolveResult` gains conditioning fields.
  Additive — existing fields and the existing call signature are
  unchanged, so current callers and tests keep working.
- `tests/`: existing solver e2e tests regroup into the two decks; new
  partial-visibility tests added.
- New fixture: a close-range rendered sequence under
  `tests/fixtures/`, generated by the existing Blender pipeline
  (`blender_video_scene.py` is reused unchanged; only camera keyframes
  differ). Blender stays a fixture-regeneration-only dependency.
- README: working-distance floor and conditioning guidance.
- No changes to `server.py`, `inject.py`, or `detect.py`.
